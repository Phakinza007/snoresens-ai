## โมเดลที่เว็บเรียก

`web_server.analyze_bytes` เรียก `predict.py` ซึ่งอ่าน threshold จาก `artifacts/mobile_metrics.json` และใช้ `yamnet_base.tflite` ร่วมกับ `snore_score_head.tflite` โดยมี `cough_score_head.tflite` เป็นหัวจำแนกเพิ่มเติมเมื่อไฟล์พร้อมใช้

ผลเก่าที่ตรงกับหัวจำแนกกรนของเว็บคือ accuracy 97.99% บน test 149 คลิป, confusion matrix `[[74, 0], [3, 72]]`, threshold 0.63 ไม่ควรนำผล embedding 100% มาแสดงเป็นคะแนนของโมเดลที่เว็บใช้ ทั้งสองผลยังไม่ได้ประเมิน dataset ซ้ำในรอบนี้

## แผนที่ทำต่อได้ในเครื่อง

1. **จัดชุดหลักฐานสไลด์** — ทำกราฟ confusion matrix และตารางเปรียบเทียบจากผลเก่าที่ตรวจที่มาแล้ว แสดงขอบเขต dataset/split และระบุโมเดลที่ใช้ในเว็บให้ตรงกัน; ROC ต้องมีคะแนนทำนายรายตัวอย่าง จึงไม่สร้างเส้นจากค่า AUC อย่างเดียว
2. **ตรวจข้อมูลสำหรับรันประเมินใหม่** — ตรวจว่ามี dataset, split เดิม, seed และตัวประมวลผลครบหรือไม่ หากครบจึงรันซ้ำ; หากไม่ครบให้ระบุว่าเป็นผลบันทึกเดิม ไม่อ้าง reproducibility เกินหลักฐาน
3. **ตรวจหน้าเว็บในเบราว์เซอร์** — อัปโหลดเดโม เลื่อน timeline ย้อนฟัง และดาวน์โหลด JSON/CSV แล้วตรวจเนื้อหาไฟล์ ยังไม่ได้ยืนยันครบในรอบนี้
4. **เตรียมโครงสไลด์และบทพูด** — pipeline, features, dataset/labels, ผลโมเดล, system test cases และ References หน้าสุดท้าย; ใช้เวลาส่วนใหญ่กับเดโมในกรอบ 8 นาที
5. **ทดสอบตัวอย่างนอกข้อมูลฝึก** — เมื่อมีเสียงรบกวนหรือเสียงบันทึกจริงพร้อมป้าย ตรวจ false positives/missed events เพิ่มก่อนสรุปข้อจำกัด

## ส่วนที่ต้องมีผู้ใช้ช่วยหรือข้อมูลเพิ่ม

- ฟังยืนยันเสียงเดโมและแก้ป้ายเวลาของเสียงจริง ไม่ใช้คำทำนายโมเดลเป็น ground truth
- ทดสอบไมโครโฟน โทรศัพท์ และสภาพห้องจริง รวมเสียงจากรูมเมท หากจะอ้างความสามารถเหล่านี้
- ตรวจชื่อ/รหัสสมาชิกและลิงก์ GitHub/Drive ที่อาจารย์เข้าถึงได้ก่อนทำสไลด์ฉบับส่ง
- การส่งงาน การเผยแพร่ และการ freeze ไฟล์หลัง deadline ต้องอ้างอิงฉบับที่ผู้ใช้ตรวจแล้ว
